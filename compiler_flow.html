00 · Python 前端 FRONTEND

从模型到"划好范围"的子图

NPU 只认识固定的一批算子组合，模型里几乎一定有它不认识的东西（自定义算子、CPU 专属的 预处理逻辑等）。这一步要做的事，是先把"能拼成硬件认识的一个大算子"的小算子链粘起来， 再把"确实能跑在 NPU 上"的连续区域圈出来，各自变成一个独立的编译单元。

分区（Compiler="exp_xxx"，之后独立编译）
qnn.conv2d→ nn.bias_add→ qnn.requantize→ clip
复合算子: conv2d_bias_req_clip
qnn.conv2d→qnn.requantize
复合算子: conv2d_bias_req

先用 MergeComposite 把一条算子链粘成一个复合算子；再用 AnnotateTarget + MergeCompilerRegions + PartitionGraph 把连续的复合算子圈进同一个分区，贴上 Compiler="exp_xxx" 的标签。

更深一层：这条链路里三个容易被忽略的机制

第一，分区不是一遍过的——中间还插了一个 recompute() pass： 对某些激活值，宁可让硬件"多算一遍"也不占着片上空间等它被消费，这是一种用计算换空间的 权衡，发生在分区定型之前。第二，cut point 有时是"造"出来的：当需要在两个 复合算子之间强行插入一条分区边界时，会先插一个临时的 blackbox 占位算子逼 MergeCompilerRegions 在那里断开，圈完之后再把占位算子摘掉 （AddRedundantBlackboxToInput / RemoveRedundantBlackboxToInput）—— 这是个有点"作弊"但很实用的技巧。第三，调用链比"shell 出去"更绕一层： relay.build() 触发 EXPJSONSerializer::serialize() 写出 _ops.json/_params.json，运行时再经 wrapper_tvm_runtime.py → run_exp_tvm.py 拼出真正的命令行， 用 subprocess.run(['bash', ...]) 起一个子进程去跑 tvm_main。

行业对照
  • 这一整套流程本质上就是 TVM 的 BYOC（Bring Your Own Codegen）机制—— 和 TVM 里接入 TensorRT、Arm Compute Library 走的是同一条 AnnotateTarget → MergeCompilerRegions → PartitionGraph 路径，只是这里的"外部代码生成器"生成的不是 另一份可执行代码，而是喂给 tvm_main 的 JSON。
  • MergeComposite 融合算子链，和 XLA 的 HLO fusion、TensorRT 的 layer fusion（Conv+Bias+ReLU 粘成一个 kernel 是教科书级别的优化）、PyTorch Inductor 的 fusion 是同一个思路：减少中间结果落地的次数。
  • recompute() 用计算换内存，和 GPU 训练框架里的 gradient checkpointing / activation recomputation（PyTorch 的 torch.utils.checkpoint）是同一个权衡，只是那边是训练时为了塞进 HBM， 这里是推理时为了塞进片上 SRAM。
分区就是随便切几刀

真正的切分点其实是靠 Chapter 05 内存分配需要多大空间反推出来的—— Tree Walker 会先跑一遍探测每层的 ring buffer 大小，算完才知道该在哪里切。

01 · 生成软件命令 LOWER · STEP 1

JSON 节点变成类型化的 Command

tvm_ops.json 里的每个算子只是一个普通 JSON 节点：一个字符串名字，一堆 attrs。 硬件编译器需要的是字段完整、类型明确的 Command——这一步就是"查表 + 翻译"， 而且严格分两级：先落一份轻量的 JobDefLite，再转成后续所有阶段都要用的 完整版 JobDef。

更深一层：qmin/qmax 怎么定，JobDefLite 为什么要单独存在

同一个量化范围其实有好几个候选来源，代码里 set_qmin_qmax() 按优先级挨个试： 先看 attrs 里显式的 _max/_min，没有就退到 a_max/a_min，再没有退到 op_attrs_output_max/_min，还没有就按 act_bits 算出对称范围（qmin=-2^(b-1)），实在什么都没有才按 dtype 兜底 （int8→[-128,127] 这种）——五级 fallback，说明这从来不是一条干净的 理论映射，而是多个信息源互相打补丁凑出来的现实。JobDefLite 单独存在 是因为算子分发（generate_lite_commands）根本不需要地址、ring buffer 这些后期才有意义的字段——先出一份轻量版，跑完 convert_job_proto_lite_to_job_proto() 才补齐 vadr_base、serial_debug_info 等字段（初始化成 0）， 变成后面几十个 pass 真正操作的完整 JobDef。

行业对照
  • 这一步等价于任何 ML 编译器的 IRGen / 算子下降阶段：XLA 把 HLO 降到 Thunk、Glow 把 Node 降到 Instruction、MLIR 把 Relay 类方言转换到更低层方言—— 都是"图节点 → 目标后端认识的具体指令"的翻译。
  • op_name_association 这张查表本质上是一个简化版的 指令选择（Instruction Selection）——类似 LLVM SelectionDAG 给 IR 节点挑机器指令，只是这里的"指令集"是有限的几十种硬件层类型，所以退化成了名字对函数 的直接映射，不需要模式匹配式的复杂 ISel。
  • 差异在于：GPU 编译器面对的是通用 ISA，可以用模板（CUTLASS）或 JIT（Triton） 现场拼出任意运算序列；这里硬件引擎的种类是固定死的（Conv、Pool、…），所以这一步更接近 DSP / 固定功能 ASIC 编译器（比如 Hexagon NN、Edge TPU 编译器）的算子目录查表， 而不是通用 GPU 后端的代码生成。
这一步已经决定内存布局了

这里生成的 JobDef 里所有和地址相关的字段都是 0，是纯粹的"运算描述"， 内存布局要等 Chapter 05 才真正发生。

更深一层：不是所有 pass 都在"融合"，也有专门"拆开"的

pad_conv_pass、multiple_concat_pass 这类是在做减法（消除多余 命令）；但 conv_fission_pass 恰恰相反——它把超过硬件单条指令处理能力的超大 卷积核，主动拆成硬件吃得下的若干小块，本质是一种编译期强制的"分块"。 serialization_optimization_pass（也就是 tvm_main_func.cpp 里 你正在改的那份文件所在的 pass）单独决定每个 tensor 用哪种片上排布模式（CPC 序列化模式）， 这个决定会直接影响后面 Tree Walker 算出来的依赖形状和 ring buffer 大小——所以它虽然发生 在排序之前，但改动会一路影响到 Chapter 03、05 的具体数字。

行业对照
  • 这种"固定顺序、几十个 pass 依次跑一遍"的结构，和 LLVM/MLIR 的 PassManager 流水线、XLA 的 HLO pass pipeline（代数化简、CSE、 layout assignment、fusion 等按固定顺序跑）本质上是一回事。
  • pad_conv_pass 把 Pad 折进 Conv 的 padding 属性，是所有推理编译器 的标准动作——TensorRT、ONNX Runtime 的图优化器都有等价的 "conv-pad fusion"。
  • conv_fission_pass 拆分超大 kernel，概念上类似 GPU 世界里的 loop tiling / kernel splitting（TVM TE 的 split 原语、Triton 的 block 配置）；区别是 GPU 那边通常是"在一个可搜索的调度空间里挑一个 tile 大小"，这里则是"硬件引擎能处理的最大块就是唯一答案"，没有调参空间。
这些 pass 谁先跑谁后跑无所谓

顺序是写死的——后面的 pass 往往假设前面的 pass 已经把某种模式清理干净了， 调换顺序很容易让某个 pass 匹配不到它期望的模式。

03 · Packet 排序 SCHEDULE · TREE WALKER

不是排层，是排行

片上的 VSP（激活值用的 SRAM）很小，通常只有几 MB；而一张真实的 feature map 可能有几十 MB。 如果老老实实"A 层全部算完存起来，再算 B 层"，要么整张图放不进 SRAM 只能落 DDR， 来回倒腾拖垮带宽；要么被迫把 SRAM 造得很大。硬件真正想要的执行方式更像一根水管： 上游一边算一边把结果一行一行喂给下游，下游消费完立刻释放。 Tree Walker 的工作，就是算出这根水管里各层的行该按什么顺序流过去。

一个 packet = 某层输出 tensor 在切片轴上的一个切片（默认是"一行"）。 一个 224 行输出的 conv 会拆成 224 个 packet；不可切片的算子（全局平均池化、 带 index 的 scatter）整体退化成 1 个 packet。每个 packet 只有三种状态：

PENDING

还没被需要，也没开始算。

→
EXECUTING

被下游要了，正在凑齐它依赖的父层 packet。

→
ON_CHIP

已经算完躺在片上，等最后一个消费者用完就释放。

顺序不是简单交替(A0,B0,A1,B1…)，而是 A0 A1 B0 A2 B1 A3 B2 A4 B3 B4—— 因为 B0 需要 A0和A1 才能凑齐，A 必须先连算两行；之后每多算一行 B， A 只需再往前吐一行新的。

这个例子的重点 A 总共 5 行输出，但全过程同时活着的行数从没超过 3——这个 3，就是 Chapter 05 真正会为 A 开辟的 VSP ring buffer 大小 （max_super_slice_rows）。网络越深、卷积核越大，收益越夸张。

顺序是怎么产生的：需求驱动的"拉"式遍历

关键心法：这不是"从输入往输出推"的顺序执行，而是从输出往输入要的按需遍历， 很像惰性求值。想发射 B0 时，实际发生的事情是：

request B0
// 3×3 感受野需要 A 的第 -1,0,1 行 → 越界不需要真实数据 → 有效依赖 {A0, A1}
A0 尚未 ON_CHIP → 压栈去算 A0
A1 尚未 ON_CHIP → 压栈去算 A1
依赖凑齐 → emit A0, emit A1
依赖凑齐 → emit B0

一般化后，gen_packet_order_pass 用一个栈做深度优先：想发射某 packet 时， 检查它依赖的父层 packet 是否都已 ON_CHIP；不是就把父层压栈，先追父层需要的行， 一路追到头（DMA 输入或已算好的行）再把栈弹回来，边弹边发射。

更深一层：这套算法比"一次遍历"复杂得多

首先，父层遍历顺序本身是可配置的：默认按 cmd_idx， 也可以按 tvm_layer_order、custom_parent_order，或者 parent_constraints（额外加跨层排序约束）——同一张图换一种模式， 交替节奏完全不同。其次，为了拿到 ring buffer 大小，Tree Walker 其实要多跑 几遍：get_cut_points() 会先以"探测模式"整体跑一遍，只为了 测出每层的 ring buffer 峰值，好反推出 Chapter 00 该在哪里切分区； auto_extra_row_pass 又会再跑一遍，专门测量 packet 之间的执行"空隙"， 自动配置额外的缓冲行数——真正决定最终 cmem.txt 顺序的，是第三次 跑。第三，"一个 packet = 一行"只是默认情况：像 Depth2SpaceIN 这类块状算子， 一个 packet 实际横跨 block_h 多行（非均匀 packet）。最后，真实顺序里 DMA 不是简单地全部排最前面就完事——还有一层同步标记插入 （pkt_sync_flag_insertion），专门决定哪些 DMA 可以和计算并行重叠、 哪些必须等一个同步点，这是在基础顺序之上又叠了一层优化。

两种会打断流水线的特殊情况

权重 / 常量 DMA — 提前到最前面

DMA 是整体的、不可切片的一个 packet，只依赖 DDR 能不能读——直接排在所有计算 packet 之前，等真正开始算的时候数据早就到位。

全局池化 / scatter — 流水线里的"墙"
等全部输入

输出的每个值都可能依赖输入的全部行，没法只看某几行先算——退化成 1 个 packet， 必须等全部输入 ON_CHIP 才能发射。

行业对照
  • 算"生产者-消费者之间最小需要同时存活的缓冲区大小"这件事，和 Halide 的 compute_at/store_at 调度推断 几乎是同一个数学问题——Halide 用区间分析算出中间 buffer 的最小尺寸，只是那边这是个 "可选的局部性优化"（不做也能跑，只是慢/占内存），这里因为压根没有缓存兜底， 是"不算出来就编译不过"的硬约束。
  • 这种"跨很多算子、按行/按块流式排列、把片上驻留压到最小"的调度模式，是 脉动阵列 / 空间数据流加速器编译器的共同特征——学术界的 Halide-to-Hardware、 工业界 Groq、Graphcore IPU 的编译器都要解决同一类问题，只是各家的"最小单元" （行、块、tile）和约束形状不同。
  • GPU 上没有直接对应物：GPU 编译器通常按 kernel（一层或几层融合） 为单位生成代码，kernel 内部靠 CUDA thread block / shared memory 做局部 tiling， 但 kernel 之间的中间结果基本靠"写回 HBM，下一个 kernel 再读"，因为 HBM 带宽和 L2 cache 足够宽裕，GPU 编译器不需要像这里一样把整张网络编译成一条固定的跨层流水线—— 这一点会在 Chapter 08 里展开讲。
这不就是个拓扑排序吗

拓扑排序解决的是"层"的顺序——几十到几百个节点，随便一个合法顺序都行。这里排的是 "packet"的顺序——可能几万个节点，而且优化目标是"让同时存活的 packet 数尽量少"， 不是"随便一个合法顺序"。

ring buffer 大小是提前配置好、写死的吗

不是。它是遍历跑完之后，根据实际发生的"哪些行同时活着"统计出来的——是遍历的 副产品，不是输入。

preemption_pass 在允许被打断的位置插入抢占标记（P2 处）； layerwise_pkt_order_pass 把 tree walker 内部按 partition 的视角"拍平"成 最终的逐层顺序；hardware_profiling_pass 再给每条命令打上性能分析用的 tag。

更深一层：还有一次单独的"权重加载"重排

除了 Tree Walker 主线的 packet 顺序，MCF 里如果配了 multi_wt_load， 还会单独触发一段 packet_reorder 逻辑：按配置的层号列表算出对应的 packet 序号（get_pkt_order_layer_from_tvm_layer），在这些位置插入额外的权重加载 命令（add_wt_cmds）——这是专门为"模型太大、权重要分批加载"场景准备的 第二层重排，独立于 Tree Walker 的主排序逻辑，也独立于后面 weight_prefetch 那次基于性能模型的重排。这一章看起来像"打标签"，实际上是好几个各自独立的收尾逻辑叠在一起。

行业对照
  • 这类"排好序之后再走一轮标记/清理"的收尾阶段，和 LLVM 里指令调度完成之后的 peephole 清理、VLIW 编译器的指令打包（bundling） 是同一层次的工作：不再改变因果关系，只是把已经定案的顺序整理成最终形式。
  • preemption_pass 插入抢占点，和 GPU 的可抢占 kernel （CUDA 的 compute preemption）解决的是同一类问题——多任务/多优先级场景下， 执行到一半也要能被打断。区别是 GPU 的抢占主要靠硬件在 SM 级别做上下文切换， 这里是编译期就把"允许在哪里打断"以显式标记的形式写死进静态程序里。
这一步还会改变谁先算谁后算

真正决定"谁先谁后"的因果关系在 Chapter 03 已经定死了，这里只是在 已经定案的顺序上贴标签，不会颠倒执行顺序。

更深一层：分配失败之后到底发生了什么

VSP 从两端往中间长：常驻的跨分区激活从顶端往下占，会被复用的 ring buffer 激活从下往上长， 两者用的是同一块地址空间，中间还有个"内存别名（aliasing）"技巧——channel 模式让不同 tensor 复用同一条 VSP 行的不同 core 切片，width 模式则是简单地 首尾相接。当某个分区的 ring buffer 深度算出来太大、VSP 放不下时， MemAllocJobProtoOptimizer 会捕获这次失败，用 add_cut_points_in_the_middle / auto_cut_point_greedy 在图里再插一个新的切分点，退回 Chapter 00-04 重新整个跑一遍——这不是理论上的可能性， 而是这颗编译器里一条真实存在、会被触发的重试循环。分配失败时的报错也不是笼统的 "OOM"，而是会具体报出最大 VSP、剩余 VSP、失败发生在哪个 partition、哪个 tensor， 以及一个建议的 cut_point——工程上是按"这次编译失败了，但至少告诉你该往哪切" 来设计的。

行业对照
  • 这种基于 liveness 的静态地址分配，和 XLA 的 buffer assignment （给 HLO 里每个逻辑 buffer 做活跃区间分析再静态摆地址）、TensorFlow Lite Micro 的 arena allocator 是同一类思路：都是"整张图跑一遍活跃性分析， 一次性把所有 buffer 的地址定下来"，而不是运行时按需 malloc/free。
  • 更贴切的 GPU 类比不是"GPU 的显存分配"——GPU 有几十 GB HBM，配合 CUDA 的 caching allocator 做运行时动态管理，出错代价通常只是"多用点显存"。真正对应的是 GPU 一个 kernel 内部的 shared memory / 寄存器分配：那也是一块 几十到几百 KB 的紧凑资源，由编译器（ptxas）在编译期静态分配， 放不下就编译失败（register spill 或 "too much shared memory" 报错）—— VSP 更像"放大版的 shared memory"，而不是"缩小版的显存"。
内存分配只是简单地从头往后摆地址

它是一个会失败、会回退重来的过程——VSP/MMP 放不下时，编译器会自动在 Chapter 00 的分区基础上插入新的切分点，重新走一遍前面的 pass， 直到能放下为止。

更深一层：一个权重 tensor 其实同时活在两个地址空间里

拿 conv 举例，HW_Command::gen_fp_conv_command() 不是只填一个地址——权重 的 weight_addr_base 来自 MMP 里的 mmp_vadr_base，同一个权重 tensor 还有一份 weight_vsp_addr_base 来自 VSP 里的 vadr_base， 因为权重要先从 MMP 搬一份"镜像"到 VSP 才能参与计算——这个细节在 Chapter 05 的内存地图 里其实已经埋了伏笔（MMP 权重区旁边配的那份"权重区（常驻）"）。另外，生成出来的 HWCommand 并不会丢掉原始的软件命令——sw_cmd 字段把整条 Command 原样拷贝进来，方便调试时能同时看到"填之前"和"填之后"。 类似 gen_fp_conv_command() 这样的函数一共有大约 70 个，覆盖 conv、pool、 concat、softmax、DMA 等几乎所有硬件命令类型，每一个都在重复同一个模式： 从 tensor_vid 读地址、从 tensor_vinfo 读 ring buffer 大小、 从 attribute 读运算参数。

行业对照
  • 这一步是经典的指令选择（Instruction Selection）后段： LLVM 的 SelectionDAG/GlobalISel 给 IR 节点挑具体机器指令并绑定寄存器/立即数， 这里 gen_fp_conv_command() 做的是同一件事——给抽象运算绑定具体的 "机器指令"（HWCommand）和具体操作数（这时地址已经全部落实）。
  • 也直接对应 GPU 编译器里 ptxas 把 PTX 虚拟寄存器 IR 降到 SASS 真实寄存器的那一步——都是"占位符 → 具体资源"的转换。
  • 差异在于粒度：GPU 的这一步通常只在单个 kernel 内部做寄存器分配 和指令选择；这里还要额外汇入一次全网络范围的调度结果（packet 顺序、 ring buffer 大小），因为整个网络是编译成一份静态程序，而不是像 GPU 那样按 kernel 逐个独立启动。
硬件化只是把地址填进去，是个机械步骤

这是唯一一个把"运算是什么、顺序是什么、放在哪儿"第一次凑到同一个结构体里的地方—— 前面任何一个阶段算错了，都会在这里第一次暴露成一个具体的错误寄存器值。

更深一层：这一步在生产环境里其实是 Python，而且还有一层压缩

mnt_gen_cmem.py 读回三份 proto，对每条命令按 op 类型查一张 OPRegistry，调用对应的打包函数，用 modify_bit / modify_bits_in_range 这类位操作把具体字段塞进 arg48/49/50 这样的固定位置（fields_to_str() 最终格式化成一行十六进制文本）。 pkt_ord.txt 的顺序还会经过一道可选的压缩—— pkt_order_compression 把重复的循环模式编码成"循环 + 偏移"的形式， 避免几万个 packet 的顺序原样铺开占用太多空间。另外一个常见的认知误区是： imem.bin（控制器微代码）根本不是这条流水线的产出—— 它来自一条完全独立的汇编流程（asm2eRiscV.py 把手写的 imem.asm 转成二进制），只是最后被一起打包进 model_bin 目录，容易被误以为和 cmem.txt 出自同一处。

行业对照
  • 把结构化字段按位打包进定长记录，概念上等价于 GPU 编译器最后一步的 SASS 二进制编码（ptxas 把解析好的指令打包成 SM 取指单元认识的确切位布局），或者更贴近 VLIW/DSP 的指令打包 （TI DSP、高通 Hexagon 的 VLIW 打包——Hexagon 甚至也把这种打包单元叫 "packet"，纯属巧合但很好记）。
  • 更根本的差异是：GPU 的 SASS 仍然是一条可识别、可反汇编的指令流 （nvdisasm 能一条条还原出指令语义）；这里的 cmem.txt 更接近定长描述符表——每一行是一个"配置好的硬件引擎该怎么跑一次"的 记录，而不是一条条被取指、译码、发射的通用指令。类比对象与其说是 CPU/GPU 的指令流， 不如说是 DMA 描述符链或者 GPU 的间接绘制/命令缓冲区 参数更贴切。
cmem.txt 里的每一行就是一条硬件指令

一行是一个 packet（可能是某层某一行的计算，也可能是一次 DMA），多条命令可能因为 融合或一次搬运多行数据而对应到一行里，一条命令也可能拆成好几行—— 行数和"层数"或"命令数"都不是一一对应的。

08 · NPU vs GPU SYSTEMS COMPARISON

两种截然不同的"把延迟藏起来"的哲学

前面八章讲的所有细节，其实都在服务同一个更大的问题：谁来决定"这一刻硬件在做 什么"——是运行时的硬件调度器，还是编译期的一份静态程序？ GPU 选了前者， 这颗 NPU 选了后者。这一章把这个核心分歧摊开讲清楚，顺便说说哪些优化思路能直接照搬， 哪些不能。以下对比基于公开可查的通用 GPU 架构与主流 ML 编译器的一般性做法， 不是针对某一家具体产品的实测数据，重点在于把"设计哲学"的差异讲透。

维度GPU这颗 NPU
执行模型 SIMT：成千上万线程分 warp 并行，硬件 warp scheduler 在运行时决定"这一刻哪个 warp 执行哪条指令" 静态数据流：整个网络的执行顺序在编译期（Ch03 Tree Walker） 一次性算死，写进 cmem.txt 就不再变
存储层级 寄存器 + shared memory/L1（几十~几百 KB，编译器管） + L2 cache（几 MB，硬件自动管理）+ HBM（几十 GB，运行时 malloc） VSP/MMP（几 MB SRAM，编译器逐字节静态分配，Ch05） + DDR（片外，显式 DMA 搬运，没有缓存兜底）
谁负责调度 硬件 warp scheduler 运行时决策，靠超量线程"隐藏"访存延迟 编译器（Tree Walker）编译期一次性决策，硬件只负责 按固定剧本执行
出错/算差的代价 通常是"变慢"——cache miss 增多、occupancy 降低， 但一般还能跑出结果 通常是"编译不过"——SRAM 放不下就是放不下，没有 L2 兜底，只能触发 Ch05 的自动切分重试

可以直接迁移的优化思路

这些是"要算什么"层面的通用图优化，本质上跟目标硬件的执行模型无关，两边都在用：

  • 算子融合——Ch00 的 MergeComposite 和 TensorRT 的 layer fusion、XLA 的 HLO fusion、PyTorch Inductor 的 fusion 是同一件事： 减少中间结果落地/搬运的次数。
  • 量化与 requantize 插入——int8/int16 校准这套在 GPU 上就是 TensorRT 的 INT8 calibration 标准流程。
  • 图分区 / 异构调度——Ch00 的 BYOC 概念（哪些子图能跑在加速器上、 哪些留在通用核上跑）和 ONNX Runtime 的 Execution Provider 分区、GPU 侧"不支持的算子 fallback 到 CPU"是同一套哲学。
  • 常量折叠、死代码消除、公共子表达式消除——这类传统编译器优化 和目标硬件无关，两边都用，Ch02 里也有等价的 pass。
  • 用重算换内存——Ch00 的 recompute() 和 GPU 训练框架里 的 activation checkpointing 是同一个权衡，只是省的资源一个是片上 SRAM， 一个是 HBM。

GPU 特有 / 这边基本不需要的

  • 依赖硬件 warp scheduler 做动态延迟隐藏——因为有 L2 cache 兜底 + 海量线程可切换，GPU 编译器不需要像 Tree Walker 那样把"每一行数据的生存窗口" 算到那么细。
  • 显存基本靠运行时 allocator（cudaMalloc / caching allocator）动态管理，编译器不需要对整个模型做一次全局静态内存规划。
  • kernel 与 kernel 之间的中间结果，默认策略就是"落一次 HBM，下一个 kernel 再读"—— 带宽和缓存宽裕到这么做通常也够用。

NPU 特有 / GPU 用不上的

  • Ch03 那种跨很多层、按行流式排列、逼出最小片上驻留的调度—— 本质上是因为没有缓存兜底、SRAM 又极其有限，编译器被迫把 GPU 里"运行时兜底"的责任， 提前搬到编译期做穷尽推导。
  • Ch05 那种逐字节的静态地址分配，以及分配失败后自动插入新切分点、 整个重编译的回退循环——GPU 世界里"内存不够"极少需要编译器介入到这个粒度。
  • Ch07 那种定长描述符式的最终产物（cmem.txt 一行对应一个硬件引擎 配置，而不是一条可反汇编的通用指令）——这源于硬件本身是若干固定功能引擎组成的阵列， 而不是一个可编程的通用核心。
如果一定要打一个比方 这颗 NPU 编译器不是"缩小版的 GPU 编译器"，更像是三样东西的合体：
Halide 的 compute_at/store_at 调度推断（算最小 buffer 需求）
+ VLIW/DSP 编译器的静态指令打包（TI DSP、Hexagon）
+ 嵌入式 ML 编译器的静态内存规划（TFLite Micro 的 arena allocator、XLA 的 buffer assignment）
而 VSP 这块资源，最贴切的类比也不是"缩小版的 GPU 显存"，而是放大版的 GPU shared memory / 寄存器堆——真正的差别是 GPU 只需要在"一个 kernel 内部" 管好这块资源，这颗 NPU 编译器要在"整个网络范围"管好它。
说明 — 本章 GPU 侧描述基于公开的通用 GPU 架构常识（SIMT/warp 调度、shared memory、caching allocator）与主流 ML 编译器公开文档（XLA、TensorRT、Halide），用于建立概念对比，非本仓库代码验证内容。

每一章的两层卷积 / 假想例子都是简化后的教学演示，用来建立直觉；真实实现还要处理多分支 fan-in/fan-out、多个 partition、几十种算子各自的依赖形状推导，以及自动切分点回退重试等一批 工程细节。核心心法不变：先定义要算什么，再定义放哪儿，最后定义什么时候真正在硬件上跑—— 而这条心法本身，正是 NPU 编译器和 GPU 编译器分道扬镳的地方。
